# Minimal Recommendation Data Schema Proposal

This proposal describes the data needed before serious ML work. The goal is to collect clean raw signals first, then derive features and models later.

## 1. User Ratings

Current base: `UserShow.userRating`.

Recommended fields:

- `userRating`: number from 0 to 10 on `UserShow`
- `ratedAt`: date on `UserShow`
- optional `ratingSource`: `manual`, `move_to_watched`, `suggestion_accept`

Why needed:

- Ratings are the strongest explicit taste signal.

Raw or derived:

- `userRating`, `ratedAt`, and `ratingSource` are raw user data.

Future recommendation value:

- Builds user taste profiles.
- Weights genres and similar shows.
- Supports rating prediction and model evaluation.

## 2. User Interests

Recommended model: `UserInterest`.

Fields:

- `user`
- `interestType`: `genre`, `mood`, `theme`, `actor`, `language`, `era`
- `value`
- `weight`
- `source`: `explicit`, `derived`
- `createdAt`, `updatedAt`

Why needed:

- Interests support cold-start users before enough ratings exist.

Raw or derived:

- Explicit interests are raw data.
- Derived interests are derived data and should be marked as such.

Future recommendation value:

- Helps rank new suggestions when a user has little watch history.
- Allows transparent preference editing later.

## 3. Interaction Events

Current base: `UserInteraction`.

Recommended additions:

- event types: `suggestion_impression`, `card_opened`, `search_performed`, `filter_used`
- `recommendationLog`
- `position`
- `modelVersion`
- `metadata`

Why needed:

- Events show what users see and how they react, not just what they rate.

Raw or derived:

- Interaction events are raw behavioral data.

Future recommendation value:

- Enables accept-rate, open-rate, and conversion-rate metrics.
- Creates training rows for accept/ignore prediction.

## 4. Recommendation Logs

Recommended model: `RecommendationLog`.

Fields:

- `user`
- `modelVersion`
- `source`: `catalog`, `tmdb`, `demo`
- `page`
- `items`: array of `{ tvShow, tmdbId, title, score, position, scoreBreakdown }`
- `createdAt`

Why needed:

- To evaluate recommendations, we must know exactly what was shown.

Raw or derived:

- Mostly derived data because scores and rankings are generated by the recommender.

Future recommendation value:

- Supports offline evaluation.
- Allows model-version comparison.
- Links feedback to the recommendation that caused it.

## 5. Recommendation Feedback

Recommended model: `RecommendationFeedback`.

Fields:

- `user`
- `recommendationLog`
- `tvShow`
- `tmdbId`
- `action`: `accepted_want`, `accepted_watching`, `accepted_watched`, `ignored`, `opened`, `rated`
- `rating`
- `createdAt`

Why needed:

- Feedback turns recommendations into supervised learning examples.

Raw or derived:

- Feedback actions are raw data.
- Aggregated feedback metrics are derived data.

Future recommendation value:

- Helps estimate which model versions work.
- Provides labels for future classifiers/rankers.
- Separates feedback on recommendations from general library actions.

## Assumptions

- Normal users should only train on their own private data plus anonymized aggregate signals later.
- Admin/demo data should not be mixed into normal user training data.
- Recommendation logging can be added before ML serving.
- The first ML-ready goal is not a neural model; it is a clean dataset.
