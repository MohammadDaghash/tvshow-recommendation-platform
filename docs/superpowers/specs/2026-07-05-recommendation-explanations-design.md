# Recommendation Explanations Design

## Goal

Add a short, natural-language explanation of *why* a show was recommended, generated by Claude, layered on top of the existing content-based `recommendationScore`/`scoreBreakdown` that `recommendation.service.js` already computes. Claude never scores or ranks anything — it only narrates numbers that already exist. This is the project's first real LLM integration; today's "AI Suggestions" surface is TMDB-sourced sorting, not an LLM call.

This design was produced by three independent proposals (backend integration, prompt/output schema, product/UX) and then adversarially critiqued twice (cost/security, architecture fit against AGENTS.md). The critiques found real contradictions between the three proposals — conflicting auth rules, three incompatible caching plans, a circuit breaker that can't work on this app's Vercel serverless deployment, and a cache-invalidation assumption that doesn't hold given how `preferenceVector` actually works. Everything below is the reconciled result, not the raw first draft.

## Architecture

**Endpoint:** `POST /api/recommendations/:id/explanation`, mounted behind `protect` (real auth required), not `optionalAuth`. `client-react/src/App.jsx:96` defines `isDemoMode = !currentUser` — in this codebase, anonymous *is* demo mode. Gating behind login is the only thing that makes the per-user daily cap (below) meaningful, and it guarantees zero Anthropic spend from anonymous/public traffic, which is unbounded on a public portfolio site.

**Request body:** the client already has `recommendationScore`, `scoreBreakdown`, and `similarWatchedShows` from the `GET /api/recommendations` response it already fetched to render the grid — send those back in the POST body instead of having the server recompute `getRecommendations(userId)` (a full-catalog rescore) just to look up one show's row. The server independently loads the canonical `TVShow` by `:id` (never trusts a client-supplied title) and does cheap bounds validation (each `scoreBreakdown` field 0-100, `similarWatchedShows` capped at 3 entries) before building a prompt — this isn't a security boundary that matters much here, it just stops a malformed/huge payload from producing a garbage prompt.

**No new persistent cache collection.** The original proposal included a `RecommendationExplanation` Mongo collection with a 30-day TTL, keyed by a hash of the score inputs, on the theory that it "self-invalidates" when scores change. That assumption doesn't hold: `createPreferenceVector` in `recommendation.service.js` builds one aggregate vector from a user's *entire* watched-show history, so rating or watching any single additional show changes `genreSimilarity` — and therefore the cache key — for nearly every other candidate simultaneously. For the exact users this feature targets (people actively rating shows), that collapses the real cache-hit rate far below what a "30-day cache" implies. Given that, a persistent explanation cache isn't worth the complexity for v1. Skip it.

**No cross-instance circuit breaker.** The app deploys to Vercel (`cinema-ws/api/index.js`, `cinema-ws/vercel.json`) as a serverless function, so in-process state (a consecutive-failure counter, an in-memory single-flight map) does not reliably persist or share across invocations — exactly when it would matter most (a real Anthropic outage means concurrent requests hit fresh, possibly cold-started instances with empty counters). Don't build one. Rely instead on a per-request timeout (`AbortController`, ~6s) and a plain try/catch fallback. This is simpler and honest about the deployment target.

**Cost control reuses existing infrastructure instead of adding new state.** `UserInteraction` already exists and is exactly the durable, Mongo-backed, serverless-safe store this needs:
- On a successful explanation render, log one `UserInteraction` row with a new `eventType: "explanation_viewed"` (added to the enum in `cinema-ws/models/UserInteraction.js`), linked to `recommendationLog`/`position` the same way `card_opened` already is, with LLM-specific facts (model id, latency, whether it was a repeat request) in the existing `metadata: Mixed` field. Do **not** write an Anthropic model id into `modelVersion` — that field is the grouping key `recommendationSignalReport.service.js` uses to compare *recommender* iterations; overloading it would silently corrupt that rollup.
- The daily cost cap is a single indexed count query — `UserInteraction.countDocuments({ user, eventType: "explanation_viewed", createdAt: { $gte: twentyFourHoursAgo } })` — against `EXPLANATION_DAILY_LIMIT_PER_USER` (default 50, code constant, no env var needed for v1). No separate rate-limit collection.
- A short-lived, best-effort in-memory guard (a small `Map` inside the service, scoped to one warm instance) prevents an obvious double-click from firing two requests in the same few seconds. Document explicitly that this is best-effort only, not a correctness guarantee, given the serverless reality above — it exists to save an obviously wasted call, not to bound cost.

**Failure handling.** The endpoint always returns HTTP 200 for LLM-specific degradation — never a 500 that implies the recommendations feature itself is broken:

```json
{ "explanation": "string or null", "cached": false, "fallback": false, "reason": null }
```

`reason` is one of `null | "disabled" | "rate_limited" | "timeout" | "unavailable" | "daily_limit_reached"`. Missing `ANTHROPIC_API_KEY` is checked once at module load and short-circuits every call to `reason: "disabled"` with no network attempt. A 404 is still used for a genuine client error (`:id` doesn't match a show in this user's catalog) — that's not a degrade-gracefully case.

**Logging must never include the raw axios error/config object.** `axios`'s error objects can serialize the outbound request's headers — including the `x-api-key` header — straight into logs. On a Vercel deployment those logs are viewable via the dashboard. Only ever log `status`, the Anthropic error `type`, and `message` for a failed Claude call.

## Prompt & Output Contract

**Model:** `claude-haiku-4-5`. This is a narrow, templated, per-show, on-demand, user-facing-latency call (paraphrase 5 numbers and up to 3 titles into 1-2 sentences under a rigid schema) — exactly the low-reasoning, high-determinism task Haiku is priced and tuned for. No `thinking`/`effort` params. `max_tokens` small (~200), non-streaming.

**System prompt:**

```
You are writing short, natural explanations for why a TV show was recommended to a
user inside a TV show recommendation app. A content-based recommendation algorithm
has already computed a numeric score breakdown for this show — your only job is to
explain that score in plain language. You never invent a score, and you never invent
facts about the show.

Hard rules:
1. Only reference the specific fields given to you in the user message (show title,
   score breakdown values, similar-watched-show titles). Never invent, assume, or
   reference plot details, characters, actors, setting, streaming availability,
   release dates, or any other fact about the show that is not present in the given
   fields.
2. Never state or imply a score, ranking, or reason that isn't supported by the given
   numbers. You are explaining an existing score, not creating a new one.
3. A value of 0 (or a missing/empty field) means "this factor contributed nothing" —
   not "this factor is bad." Never fabricate a plausible-sounding reason to explain
   a zero, and never build the explanation around a zero-valued factor.
4. If similarWatchedShows is empty, do not claim the show is "similar to what you've
   watched" or reference the user's taste/history at all. Base the explanation only
   on the non-zero scoreBreakdown fields, or use the cold-start framing described in
   the user message.
5. Never mention a show title other than the recommended show itself or a title that
   appears verbatim in similarWatchedShows.
6. Write in a natural, conversational tone — like a quick reason a friend would give,
   not a report. Never use technical terms like "cosine similarity," "vector,"
   "score," "algorithm," or field names such as "genreSimilarity."
7. Keep the explanation to 1-2 sentences and under 40 words total.
8. Respond with JSON only, matching the given schema — no markdown, no preamble, no
   trailing commentary.
```

**User prompt template** (placeholders filled server-side from the request body, after validation):

```
Recommended show: {{showTitle}}

Score breakdown (0-100 scale; 0 means that factor had no signal for this show, not
that it was scored poorly):
- genreSimilarity: {{scoreBreakdown.genreSimilarity}} — how closely this show's genres
  match the genres of shows the user rated highly
- categoryPreference: {{scoreBreakdown.categoryPreference}} — how well this matches
  patterns across the user's whole watch history
- tmdbRating: {{scoreBreakdown.tmdbRating}} — general audience rating quality
- popularity: {{scoreBreakdown.popularity}} — how popular/mainstream the show is
- yearSimilarity: {{scoreBreakdown.yearSimilarity}} — how close its release year is to
  the years of shows the user watched

Shows from the user's watch history most similar to this recommendation (empty array
means the user has no watch history yet, or nothing similar was found):
{{similarWatchedShows}}

Personalization available: {{hasPersonalizationSignal}}
(true only if genreSimilarity > 0 OR categoryPreference > 0 OR similarWatchedShows is
non-empty; if false, this user has no usable watch history yet — do not reference
their taste, history, or similarity to anything they've watched)

Using ONLY the data above:
- If Personalization available is true: identify the 1-2 highest-value factors and
  center the explanation on those. You may name at most one title from
  similarWatchedShows, exactly as written.
- If Personalization available is false: do not personalize. Give a brief, honest
  reason grounded only in tmdbRating/popularity, or state plainly that this is a
  general pick while we learn the user's taste. Do not say "based on your taste."

Respond with JSON only, matching this schema:
{"explanation": string, "emphasizedFactor": "genre" | "quality" | "similarity" | "general"}
```

`hasPersonalizationSignal` and a broader `hasAnySignal` (also true if `tmdbRating`/`popularity` > 0) are computed in code, not inferred by the model — this is what stops a zero-history user's explanation from hallucinating "based on your taste." If `hasAnySignal` is false (a genuinely low-signal candidate — e.g. a newly added show with no TMDB data yet), **skip the Claude call entirely** and return a fixed string ("Added to your recommendations — we don't have enough data yet to explain this one.") with `emphasizedFactor: "general"`. That's a code-level guard, not a prompt instruction, because it's free and 100% guaranteed non-fabricated.

**Output contract:** structured JSON via `output_config: { format: { type: "json_schema", schema } }` (Haiku 4.5 supports structured outputs, enforced server-side):

```json
{
  "type": "object",
  "properties": {
    "explanation": { "type": "string" },
    "emphasizedFactor": { "type": "string", "enum": ["genre", "quality", "similarity", "general"] }
  },
  "required": ["explanation", "emphasizedFactor"],
  "additionalProperties": false
}
```

`emphasizedFactor` lets the client render a small badge ("🎭 Genre match", "⭐ Highly rated") without re-parsing prose, and doubles as a cheap consistency check server-side (see guardrails).

**Guardrails on the response, layered, not prompt-only:**
- Title allow-list: any show name in `explanation` must be `showTitle` or a `similarWatchedShows[].title` verbatim; otherwise discard and use the fixed fallback string.
- `emphasizedFactor` must correspond to an actually-elevated field (e.g. `"genre"` implies `genreSimilarity` or `categoryPreference` is meaningfully > 0); a mismatch is logged and the response falls back rather than shipping.
- `explanation` must be non-empty and under ~220 characters; otherwise fallback.

## Data Flow

1. Client already holds `recommendationScore`/`scoreBreakdown`/`similarWatchedShows` for a show from its last `GET /api/recommendations` fetch.
2. User clicks an explicit "Why this pick?" affordance inside the already-open `DetailsModal` (`client-react/src/components/AppModals.jsx`) — not on card render, not on hover. This only applies to the "Recommended" tab (`scoreBreakdown` exists); the TMDB-backed "AI Suggestions" tab has no `scoreBreakdown` and is out of scope.
3. Client POSTs the echoed score data to `/api/recommendations/:id/explanation`.
4. Server: `protect` middleware requires auth → validate body ranges → load canonical `TVShow` by `:id` → check daily cap via `UserInteraction` count → check `hasAnySignal`; skip-to-fallback if false → call Claude (Haiku, ~6s timeout) → validate response against guardrails → on success, write one `UserInteraction` row (`explanation_viewed`) → return the contract shape.
5. Client renders the existing numeric `scoreBreakdown`/similarity sentence immediately and unconditionally, as today; the Claude text is a progressive enhancement underneath with its own small loading/error state. Failure never blocks or replaces the numeric explainability UI that already exists.

State lives in a new hook, `client-react/src/hooks/useRecommendationExplanation.js`, owned by `AppModals.jsx` (which has headroom — ~418 lines) — **not** in `App.jsx`, which is already at 999 lines (`wc -l client-react/src/App.jsx`) and would breach the AGENTS.md 1000-line cap if this state were added there as originally suggested.

## Observability

Extend `recommendationSignalReport.service.js`'s existing per-row counters (`opens`, `accepts`, `ignored`, `openRate`, `acceptanceRate`) with `explanationViews` and `explanationViewRate` (`explanationViews / opens`), surfaced in `TrainingHealthPanel.jsx` next to the existing coverage stats. This reuses the dashboard that already exists rather than adding a new one, and gives a real adoption/cost signal ("of the detail views, how many pulled an LLM explanation").

## README

Extend the existing "Explainable recommendation breakdowns" bullet under "What This Demonstrates" — do not add a separate "AI/LLM integration" bullet, which reads as a bolt-on:

> Claude-generated natural-language explanations layered on top of the existing cosine-similarity score breakdown — the LLM narrates a deterministic score it never computes, demonstrating a hybrid stats+LLM architecture where the recommender stays the source of truth and the model is a formatting/communication layer.

## What Makes This Feel Cheap vs. Genuinely Hybrid

Do: pass only concrete `scoreBreakdown` fields and `similarWatchedShows` titles into the prompt; cache/dedupe naturally via the daily-cap + best-effort in-memory guard rather than a fragile persistent cache; keep the recommender the single source of truth for score and ranking; make the whole feature optional/skippable (the app is 100% functional and explainable via numbers alone if Claude is down or disabled).

Don't: surface it on the card face or auto-render on hover (a chatty caption on every grid tile is the most recognizable "I called ChatGPT" tell — keep it behind an explicit ask inside the detail view); let Claude touch ranking/score/its own "match %"; turn it into a free-text "ask about this show" chat box (a different, unscoped feature).

## Testing

New `cinema-ws/services/recommendationExplanation.service.test.js`, matching the existing co-located `*.test.js` convention (every current service in `cinema-ws/services/` has one), covering as pure-function/mocked-network unit tests:
- `hasPersonalizationSignal` / `hasAnySignal` branching
- the zero-signal skip-the-LLM-call fallback
- title allow-list rejection
- `emphasizedFactor` consistency check
- daily-cap short-circuit

## Scope for v1

Ship: the endpoint, the prompt/guardrails, the frontend hook + button, the `UserInteraction` enum addition, and tests. Treat the `recommendationSignalReport.service.js`/`TrainingHealthPanel.jsx` counters as a small, separate follow-up slice once the core feature is live — this keeps the first slice close to the size of this repo's recent commits (e.g. "Simplify training health dashboard," "Count library taste data in training health") rather than a big-bang rewrite touching backend, prompt, frontend, and reporting all at once.
